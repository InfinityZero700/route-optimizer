# Route Optimizer

**Comparing Dijkstra's algorithm and A* search on real street networks using Python, graph theory, and geographic distance estimates.**

This educational applied mathematics project downloads a drivable street network from [OpenStreetMap](https://www.openstreetmap.org/) through [OSMnx](https://osmnx.readthedocs.io/), then compares two shortest-path algorithms implemented in Python. Both minimize **road distance (meters)**; A* uses a geographic heuristic to prioritize promising intersections. The tool produces per-route results, a summary chart, and an interactive HTML route map.

> **Project status:** Source code and offline unit tests are included. Real-world benchmarks must be generated by running the project; no performance percentages are claimed before measurement.

## What this project investigates

- Does goal-directed A* expand fewer intersections than uninformed Dijkstra on the same road graph?
- Do both algorithms find the same minimum-distance route?
- How do runtime and number of explored nodes vary between origin–destination pairs?

Dijkstra prioritizes accumulated distance from the origin. A* prioritizes accumulated distance **plus** estimated remaining distance. Depending on the graph and trip, A* may explore fewer nodes, but it is not guaranteed to be faster because evaluating the heuristic has its own cost.

## Algorithms and mathematical model

Represent the road network as a directed weighted graph \(G=(V,E)\), where intersections are nodes and road segments are edges with nonnegative lengths \(w(u,v)\). One-way streets are preserved.

### Dijkstra

Priority: \(f(n)=g(n)\), where \(g(n)\) is the shortest distance discovered from the start to node \(n\).

### A* search

Priority:

$$f(n)=g(n)+h(n)$$

Here \(h(n)\) estimates the remaining distance to the destination using the **Haversine** great-circle distance between GPS coordinates.

$$a=\sin^2\!\left(\frac{\Delta\phi}{2}\right)+\cos(\phi_1)\cos(\phi_2)\sin^2\!\left(\frac{\Delta\lambda}{2}\right)$$

$$h(n)=2R\operatorname{atan2}\!\left(\sqrt a,\sqrt{1-a}\right),\qquad R=6{,}371{,}000\ \mathrm{m}$$

Latitude \(\phi\) and longitude \(\lambda\) are measured in radians.

**Why the heuristic can preserve optimality:** On a spherical Earth model, great-circle distance obeys the triangle inequality. If each road edge's cost is at least the great-circle separation of its endpoints, then for every edge \((u,v)\):

$$h(u)\le w(u,v)+h(v)$$

This is *consistency*. It also implies *admissibility* (the heuristic is never greater than the minimum remaining path cost), allowing A* to return an optimal route. This project uses the typical OSMnx `length` attribute in meters; the proof relies on that lower-bound assumption, which may be affected by real-world coordinate/length approximation details. A mismatch between solvers triggers an error rather than reporting a misleading result.

Both algorithms use a min-priority queue (`heapq`) and reconstruct the chosen path using predecessor links. Parallel edges between the same two nodes are handled by selecting the shortest one. The implementation benchmarks one destination at a time, not all-destinations shortest paths.

## Requirements

- Python 3.11 or newer, Git, and an internet connection for the *first* road-network download (and for Folium's online map tiles)
- A Python virtual environment is recommended

## Setup

Clone your repository after publishing it, or unzip this project into a directory.

**Windows PowerShell**

```powershell
cd network-route-optimizer
py -3 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements-dev.txt
```

If PowerShell blocks activation, you can instead run `\.venv\Scripts\python.exe main.py` (and use that executable with `-m pip` for installation).

**macOS/Linux**

```bash
cd network-route-optimizer
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements-dev.txt
```

## Run a benchmark

```bash
python main.py --place "Bellevue, Washington, USA" --pairs 10 --seed 42
```

`--place` accepts a place name recognized by OSMnx. `--pairs` controls the number of randomly selected origin–destination pairs; `--seed` makes pair selection repeatable. The script uses the largest strongly connected road component so a route should exist between any selected pair.

**Generated files** (inside `outputs/`):

| File | Description |
| --- | --- |
| `benchmark_results.csv` | Route distance, nodes explored, and timing for each solver and pair |
| `benchmark_comparison.png` | Comparison of mean expanded nodes |
| `route_comparison.html` | Interactive map showing the first A* route |

These are excluded from Git by default. After running the project and verifying outputs, you can place a selected, real screenshot in `assets/` and link it here.

### How to interpret the data

For \(N\) tested routes, compute the average nodes explored by each algorithm. The percentage change in exploration is:

$$100\left(\frac{\overline{N}_{A^*}}{\overline{N}_{Dijkstra}}-1\right)\%$$

A negative value means A* expanded fewer nodes. Timing measurements may vary with computer load and Python overhead; repeat benchmarks before drawing conclusions. No hard-coded or invented performance claims appear in this README.

## Validate the implementation

```bash
python -m pytest -q
```

The offline tests exercise a tiny directed multigraph, path optimality against NetworkX, an unreachable destination, trivial paths, basic Haversine calculations, and invalid edge weights. These tests do not require OSM network access.

## Limitations and next steps

- The objective is **shortest geometric road distance**, not estimated traffic time, fuel consumption, or energy use.
- Street map data comes from OpenStreetMap and can be incomplete or outdated.
- Random-pair benchmarks are exploratory rather than controlled claims about all road networks.
- Haversine distance assumes spherical geometry and edge weights consistent with that geometry.
- The routing code is written for clarity rather than high-performance production navigation.

Possible extensions: let users select origin/destination coordinates, benchmark multiple cities and distances, compute confidence intervals on runtime, compare with NetworkX at scale, or support time-weighted routing with an appropriately scaled admissible heuristic.
